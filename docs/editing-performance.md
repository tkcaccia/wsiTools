# Annotation editing performance

Hold **Ctrl** and double-click a tissue annotation to select it while Brush or
Wand remains active. This also works in multi-view panes and uses the Control
key on macOS. Ctrl-clicks do not paint or run the Wand. Release Ctrl to resume
editing; clicking empty space with Ctrl leaves the selection unchanged.

## Scope

These editing-focused updates change the shared viewer generated by R,
including viewers opened by wsiTools Desktop. It does not replace
OpenSeadragon, convert tissue ROIs to masks, or simplify their original
boundaries. Close zoom continues to request the original image's maximum
Deep Zoom level.

Completed annotation paths and subtraction holes are cached until their
geometry changes. A separate, pointer-transparent canvas displays the brush
cursor and unfinished stroke. Ordinary pointer movement does not rebuild all
annotation paths, labels, spatial overlays, or the navigator.

During painting, only the newest stroke segment is tested against nearby
annotation boundaries using bounding boxes and a cached segment tree. On
release, a browser worker clips the stroke, applies union/subtraction and
class-overlap protection, and returns the edited geometry. The UI keeps the
stroke visible while this completes. A second brush edit waits for the first;
the user can cancel with Escape. Results are not applied after a tissue switch
or a conflicting geometry change.

The worker uses bundled Clipper2 WebAssembly under the Boost Software License,
with JavaScript Clipper as a fallback if WebAssembly initialization fails. Clipping
uses 1/4096 slide-pixel precision and restores unchanged original vertices.
Its code is embedded in the viewer, so editing does not download a geometry
library at runtime. No GPU or desktop-only geometry engine is required. A
restrictive custom Content Security Policy must permit `worker-src blob:` and
WebAssembly compilation. Worker failures leave the existing ROI unchanged and are
recorded in the viewer log.

Magic Wand uses filled outer selection boundaries: internal colour gaps do not
become holes. This also applies when painting editable TIFF masks or subtracting
with Alt/Command. Overlap protection is applied afterwards, so a protected class
inside the selection remains excluded. Existing holes outside a priority-added
Wand selection are not changed.

Each Wand click is confined to the circular **Reach** around the pointer (256
screen pixels by default; adjustable from 64 to 512 px). The viewer captures and
flood-fills only that local image window, so a connected colour cannot propagate
through the complete tissue or visible viewport. The resulting boundary is
simplified at the current zoom and capped at 768 vertices before it reaches the
geometry worker. This affects only newly generated Wand vertices; pre-existing
annotation boundaries retain their original coordinates.

Only new or changed candidate geometries are sent to the worker. Transport uses
transferable Float64 coordinate buffers with Uint32 ring/polygon offsets rather
than deeply nested object cloning. The worker retains prepared geometry across
strokes and evicts least-recently-used sources against a 128-MiB **estimated**
cache budget. This is not a hard process-memory limit: an active edit, JS objects,
the WebAssembly heap and temporary results can exceed it. Transfer avoids a
message-copy step; initial packing, unpacking and native-library input are not
zero-copy. Switching tissue resets the geometry cache.

For local edits, the worker clips only polygon components and holes whose bounds
intersect the stroke. Unaffected rings retain their exact original coordinates.
If a split makes hole ownership ambiguous, complete-feature clipping is used
as a conservative fallback. No display simplification or mask conversion is
introduced. A changed-ring response references unchanged rings already held by
the browser, which can reuse their component paths and hit-test indexes.
The WASM kernel uses opaque vertex provenance rather than allocating string keys
for every input vertex. Native inputs are prepared lazily.

## R synchronization and undo

Routine viewport, selection, and annotation events use compact messages.
Annotation patches contain changed features, removed IDs, and ordering, not
unchanged coordinate arrays. Each message carries a client ID, tissue key,
revision, and previous acknowledged revision. R validates these before
applying a patch. Replayed requests are idempotent; a missing baseline or
revision mismatch requires a full snapshot.

Initialization, tissue switches, explicit full-state operations, and recovery
still send snapshots. Other event types retain the previous full-state path
until separately optimized. Expression assays remain in R.

Brush and priority-Wand undo records contain only changed annotations, including
neighbours trimmed by Caps Lock. An imported neighbour is restored to its original
layer when undone. Creation, deletion and neighbour changes form one transaction.
Other tools retain the existing snapshot path. Canonical polygon histories share
snapshots of unchanged components, but those snapshots never alias live editable
points. Modified components are copied. Noncanonical geometry falls back to a
complete geometry snapshot, and undo restoration still copies the selected
snapshot. Annotation undo is limited to 10 actions and an estimated 64-MiB
geometry budget; the newest action is retained even when it alone exceeds that
budget so the last edit remains reversible.
R synchronization remains feature-based, not ring-based: each changed feature's
complete geometry is sent to R. The small ring patches described above are only
the browser/worker protocol.

Geometry-only edits refresh existing annotation-list rows without rebuilding the
whole list. Structural changes and non-default sorting still rebuild it. Explicit
changed-feature patches avoid scanning all geometry for ordinary brush edits;
viewport-only messages do not compare annotation collections. Queued edits whose
baseline has not yet been acknowledged use a complete changed-feature comparison
to avoid dropping earlier changes. R accepts an omitted ordering list when feature
order is unchanged.

Use a newly generated viewer after updating the package. An already-open HTML
page contains the older JavaScript. Keep R running and wait for synchronization
before retrieving or saving results:

```r
viewer$get_rois()
viewer$get_selected_roi()
viewer$get_performance()
```

Zero-time session polling is non-blocking. The performance report includes
`editing` counters for cursor drawing, geometry-worker time, commit time,
cached path construction and pane redraws, plus `sync` message/payload counters.
Worker time is separate from UI-thread commit time; neither alone measures
end-to-end input latency. Worker time measures the clipping operation, not initial
WASM loading, input preparation or all serialization. Payload size counts JavaScript string units and is
an approximate byte count for non-ASCII labels.

## Verification and remaining work

Regression checks cover extension, repeated subtraction, holes, different-class
and locked-region protection, merging, stable-ID deletion/undo, replayed sync
requests, and rejection of stale or cross-tissue patches.

Real-image checks should use cold and warm caches separately. Exercise:

1. Open a large tissue image with detailed GeoJSON annotations and inspect both
   zoomed-out boundaries and full-resolution image tiles at close zoom.
2. Select an imported region; paint, subtract repeatedly, undo and redo.
   Compare the browser GeoJSON coordinates with `viewer$get_rois()` in R.
3. Move the idle brush cursor: cached path construction should remain unchanged.
4. Open four spatial tissues, zoom one independently, brush only that tissue,
   undo/redo and colour a gene. Verify that other tissues retain their state.
5. Switch tissue or press Escape while clipping is pending. No stale edit
   should be applied. Confirm that pointer location matches the brush footprint.

The engineering targets are under 50 ms for tool/cursor feedback and a
16--33 ms navigation frame budget on the test machine, not guaranteed timings.
First-time path construction, large edits, spatial-layer updates and cold tile
generation can still exceed those targets.

For maintainers, `node tests/browser/geometry-worker.cjs` runs the worker
regressions without a browser; set `WSITOOLS_TEST_GEOMETRY_ENGINE=js` to test the
fallback. `edit-transactions.cjs` and `sync-patches.cjs` test sparse undo and
queued synchronization. `tests/browser/live-editing.cjs` uses Playwright
and Chrome against `WSITOOLS_TEST_URL`, a disposable local live viewer. It
creates temporary screenshots, browser GeoJSON, and a timing report. Use a
four-slide SpatialExperiment session with `Mbp` expression, or a single image
with an imported tissue layer containing detailed polygons. Never point this
editing test at a session with unsaved work. Compare its exported browser
GeoJSON with `viewer$get_rois()` and inspect the screenshots; a successful
notification alone is not visual validation.

Set `WSITOOLS_TEST_LARGEST=true` to exercise the largest imported region; also set
`WSITOOLS_TEST_LARGEST_PART=true` to anchor the stroke on its largest component.
`component-cache.cjs` checks path reuse and snapshot isolation, and
`tools/benchmarks/annotation-audit/local-components.cjs` compares component-local
and complete-feature clipping on a supplied GeoJSON file.
`tests/browser/live-priority-edit.cjs` applies the priority-edit path to the real
largest colorectal region and a neighbouring imported polygon, then checks exact
undo/redo. Its output can be checked independently using
`Rscript tests/browser/validate-priority.R /path/to/report.json` with `sf`/GEOS.

These architecture updates do **not** add FlatGeobuf/PMTiles storage, vector
display tiles, GPU polygon tessellation, a global annotation R-tree, or an on-disk
edit journal. These remain subsequent stages. Full-detail Canvas drawing can still
exceed the frame budget when large regions change or first enter the viewport.

## Measured acceptance run

### Component-local breast update: 9 September 2026

The user-supplied breast crop (`crop_roi.tif`, 43,458 x 39,886 pixels) was opened
with its 8.2-MB native-fidelity GeoJSON. All **485,941 vertices** were loaded:
three classes containing 1,102 polygon components. The brush test targeted the
largest class (242,952 vertices) at its largest outer ring (44,176 vertices).
This is not a test of a single 485,941-vertex continuous boundary.

The same Apple M3/8-GiB Mac, desktop R launcher and Chrome were used. Three
sequential trials from the normal installed R library, without competing
regression jobs, produced:

| Check | Previous live run | Installed update |
| --- | --- | --- |
| Brush addition, release to completion | 453 ms | 123--196 ms (median 124) |
| Brush subtraction, release to completion | 129 ms | 55--79 ms (median 55) |
| Priority-Wand worker/commit path, including neighbour trimming | 330 ms | 203 ms |
| Tool selection to next animation frame | 2.1 ms | 4.5--12.5 ms |
| Original-resolution image tiles | Level 16 | Level 16, successful |
| Browser/R-sync errors | None | None |

There is one pre-update baseline, not a statistical performance study. Mouse
release timing excludes the subsequent R acknowledgement, which was checked
separately. Under competing test load, addition/subtraction took 596/336 ms;
these raw results are retained rather than presented as guaranteed latency.
Annotation redraw averages were still 23--26 ms in the installed trials, so
not every rendering operation meets a 16-ms frame budget.

Screenshots were inspected for the tissue and edited boundaries. Real mouse
strokes, subtraction, exact undo, R acknowledgement and maximum-level tile
loading passed in all three final trials. The priority geometry path also
passed exact undo/redo and an independent GEOS check: valid polygons, selected
area increased, neighbour area decreased, and zero overlap.

A separate microbenchmark compares complete-feature and component-local clipping
with the same updated WASM kernel. All nine union/difference/intersection checks
across the three classes had zero symmetric-difference area. These isolated
kernel timings must not be equated with live editing latency.

[Raw results](../tools/benchmarks/annotation-audit/results/breast-local-editing.json)
include baseline, installed trials and the kernel comparison. Tests used Chrome
and the desktop R launcher, not a new Tauri binary or Windows/Linux WebViews.
The package was reinstalled locally; an existing viewer must be recreated to
load the updated embedded JavaScript. A Tauri rebuild is not needed for these
shared-runtime changes. Very large single components and full-feature R payloads
remain potential bottlenecks; this update is component-local, not tile-local
boundary splicing.

### Installed WebAssembly update: 9 September 2026

The final run used the normal local R library, the desktop R launcher and an
isolated Chrome browser on an Apple M3 Mac with 8 GiB RAM. The colorectal BTF
was opened with all 359 polygonal tissue annotations. The disk tile cache was
warm. The edited region contained **117,669 original vertices**.

| Check | Observed result |
| --- | --- |
| Brush toolbar click to next animation frame | 1.7 ms |
| Largest-region brush addition, mouse release to completion | 340 ms |
| Largest-region subtraction, mouse release to completion | 159 ms |
| Priority-Wand geometry/commit path, real imported neighbour | 290 ms |
| Maximum brush-cursor drawing work | 1.2 ms |
| Annotation redraw average / maximum in this sequence | 6.63 / 86.7 ms |
| First image tile in the warm-cache run | 248 ms |
| Original-resolution tiles | Level 17 loaded successfully |
| Browser, sync and tile failures in final run | None |

Undo and redo restored both priority-edited geometries exactly. An independent
`sf`/GEOS check confirmed valid polygons, increased selected area and reduced
neighbour area. Residual overlap was 0.000500452 square pixels, below the
0.01-square-pixel test tolerance for subpixel intersection rounding.

The production-kernel microbenchmark includes input preparation and output
reconstruction at the same 1/4096-pixel precision. Three WASM union runs took
351--422 ms and three difference runs 276--360 ms. The legacy JS batch exceeded
its **20-second total batch budget**; it is not a per-operation timing. Do not
turn this timeout into a claimed end-to-end speedup factor.

[Machine-readable results](../tools/benchmarks/annotation-audit/results/tissue-editing-wasm.json)
include raw timings and logs; the same folder contains the preceding audit
benchmarks. The live tests exercise the shared browser runtime and the desktop
R launch script, not the native starter GUI. Windows/Linux and four-pane
performance were not remeasured for this kernel update. Large initial redraws
still exceed the target frame budget; tiled annotation rendering remains future
work.

### Earlier shared-runtime acceptance run

The September 2026 macOS acceptance run used the colorectal BTF and its
12.7-MB tissue GeoJSON through the same R launcher bundled in wsiTools Desktop.
The viewer window was not exposed until the first preview existed. In a fresh
browser page, tissue pixels appeared after 1.30 s and all 359 tissue regions
after 2.66 s. Navigation retained all regions and made exactly one GeoJSON
request; no R-side dense-annotation rediscovery request was made.

Brush add, subtraction, undo, R acknowledgement, and maximum-level tile access
then passed in one automated browser workflow. Tool feedback was 1.9 ms,
maximum cursor-frame work was 0.6 ms, and the two geometry-worker operations
used 335 ms off the UI thread with 1.7 ms of UI-thread commit work. The close
zoom loaded level 17 tiles from the original image. Peak resident memory across
the R bridge, two tile workers, and the annotation worker was 373,488 KB during
this workload; browser JavaScript heap was approximately 94 MB after startup
navigation.

The same acceptance suite separately covers an OpenSlide SVS with three native
pyramid levels and a four-image project. In the four-image project, seven rapid
switches completed in 51--61 ms, each image retained a distinct fingerprinted
tile source, and only the targeted pane changed zoom. An uncached overview tile
decode took 1.82 s while an R/WebSocket event was acknowledged in 143 ms,
demonstrating that tile decoding did not block live synchronization.

These figures describe the named test data and machine, not general performance
guarantees. Browser heap and process RSS measure different memory domains and
must not be added together.
